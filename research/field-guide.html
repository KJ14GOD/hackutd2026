The big picture

Before any detail, hold one loop in your head. Every chapter explains one part of it.

Map the code→Pick a loose piece→Rewrite it→Run old and new side by side→Ask a person when unsure→Lock the answer into a test→Cut over
In plain words

Why this is hard at all

Translating old code into new code is now cheap. AI does it in seconds. What stays expensive is knowing whether the old behavior was a rule someone depends on or a bug nobody noticed. That knowledge was never written down. It sits in people's heads.

So the project is really two problems glued together: a code problem (split the system so you can safely change one piece) and a people problem (get the missing knowledge out of humans without wasting their time).

The three ideas that hold it together

If you remember nothing else

  1. AI is strong on form and weak on content. It writes valid diagrams and code, but it can't tell who holds the knowledge or what depends on what. That's why people stay in the loop. Chapter 2.
  2. Bugs cluster where code is tangled. Isolating loose pieces first targets the risk directly. Chapter 1.
  3. People can't simply tell you what they know. They describe solutions, skip the obvious, and can't imagine what they haven't seen. So how you ask matters as much as whom. Chapter 7.
The deliverable is not new code. It's old knowledge, turned into tests that keep it true.
How to use this guide

Read in order, answer before you peek

Each chapter goes from plain words, to how it actually works, to a real failure, to how it shapes our agent. Each ends with questions. Write your answer before revealing ours: getting it wrong first is how this sticks.

Sources throughout: Dr. Şeker's CS 3354 lectures (UTD, Fall 2026), L2–L18, plus the studies and cases they cite.

Coupling and seams

How to tell which parts of a codebase can be pulled apart, and why that's also where the bugs are.

In plain words

Think of a codebase as a web of strings

Each file or module is a pin. Every import or call is a string between two pins. Pull one pin and everything tied to it moves. A piece you can safely replace is one with very few strings leaving it. Those thin spots between clusters are the seams.

How it actually works

From graph to segments

  1. Build the dependency graph. Nodes are modules; edges are imports, calls, and shared database tables.
  2. Collapse cycles. If A needs B and B needs A (a strongly connected component), they can't be separated. Treat the cycle as one node.
  3. Look for disconnected groups. Groups with no path between them are fully independent. Real systems rarely have these.
  4. Find the thinnest seams. Use clustering (community detection) to find groups that are dense inside and sparse between. The few edges between groups are what you'd refactor.

Not all strings are equal. Coupling has levels, from worst to best:

LevelWhat it meansExample
ContentOne module reaches inside another and changes its internalsWriting to another component's private store
CommonModules share global data nobody ownsA shared mutable config object
ControlOne module passes a flag that steers another's logicprocess(request, mode=2)
StampA whole record is passed when two fields are usedPassing the full Student to get an ID
DataOnly the needed values travelhasSlotNow(cardId, doorId)

The test that works without the table: "If I change the inside of this module, how many other modules must I open?" The answer is a count, not an opinion.

Information hiding is the cure. Put what's likely to change (a business rule, a storage format) behind a stable interface. Ask a question (hasSlotNow()) instead of fetching the data and deciding yourself. Then the rule lives in one place.

A real case

Coupling predicted the defects

Two industrial C/C++ systems, each over ten years old (~20,000 files). The tightly coupled "core" was 26% of the files but took 62% of all defect-fixing work. Core files were about 3× more defect-prone, even after controlling for file size and complexity. The coupling itself predicted the bugs.
MacCormack and Sturtevant, Journal of Systems and Software, 2016 (L15)
In our agent

What this changes

  • Rank candidate components by boundary width (fewest edges out), weighted by coupling level, plus existing test coverage. Start with the easiest.
  • Build the graph with static analysis and git history. Add shared database tables and files that always change together as edges, because imports alone miss them.
  • When one business rule appears in several callers, that's a question for a person: which version is correct? Then move it to one place.
Trap: decoupling isn't free. Every boundary is something that must be crossed at run time. Amazon Prime Video's textbook-decoupled monitoring service handled only 5% of its needed load until they removed boundaries, which also cut cost 90% (L15).
Check yourself

Two modules share no imports, yet changing one keeps breaking the other. What kind of hidden coupling should you suspect, and how would you detect it?

Write an answer first.

Shared data: they read or write the same database table, file, or config (common coupling through a store). Detect it by adding table and file access as graph edges, and by mining git history for files that change together (co-change, or "logical coupling").

Why does "ask a question, don't fetch the data" reduce coupling?

Write an answer first.

If callers fetch raw data and decide for themselves, each caller holds a copy of the rule. Change the rule and every caller must change. If they ask the owning component, the rule lives in one place and no caller depends on the data's shape.

Form vs. content

Why the AI can write the code but can't be trusted to decide what's true.

In plain words

Fluent isn't the same as correct

An LLM is very good at producing things that look right: valid syntax, proper notation, the right vocabulary. It's much worse at the parts that need knowledge of this business: who the real users are, what depends on what, what each thing must hold. Its errors don't announce themselves. They look finished.

How it actually works

A real case

Almost right, but not quite

In the 2025 Stack Overflow survey (49,009 developers), 84% used or planned to use AI tools but only 29% trusted the output. The top frustration, cited by 66%: "AI solutions that are almost right, but not quite." That's tolerable for a snippet you'll run. It's dangerous for a model you'll build on, because a wrong actor doesn't throw an error; it produces a system that works perfectly for the wrong person.
L11
In our agent

Split the work by strength

  • Machines: build the dependency graph with static analysis (not an LLM), rewrite code, phrase questions, draft tests.
  • People: decide what's true, who owns it, and which behavior is correct.
  • The rule from L13: use the model after you've decided what's true, not to decide it.
Trap: AI-built projects drift into "manager" god classes. Smells grow with code volume (ρ = 0.94). Files look modular while responsibilities are fused, which the authors call the Modular Mirage (L17). Check the rewrite's structure, not just its output.
Check yourself

Our pitch says the agent asks people "who owns this?" Which number on this page justifies that most directly, and why?

Write an answer first.

Actor identification at 31%. Actors are the roles that hold knowledge and use the system, so routing a question to the right person is exactly the step AI does worst. Learning from "Not me →" replies targets that gap.

Replace one piece at a time

Why the safe way to modernize is gradual, and what "done" really means.

In plain words

Grow the new around the old

A strangler fig grows around a tree until the tree is gone. You do the same with a legacy system: put a switch in front of one component, build the new version behind it, move traffic over gradually, and repeat. At no point is everything broken at once.

How it actually works

Three techniques

  1. Branch by abstraction. Put an interface in front of the component so old and new are interchangeable.
  2. Gradual cutover. Route 1%, then 10%, then 100% of traffic, using feature flags. CometPark v2 rolled out one garage at a time (L5).
  3. Guardrails. A canary to limit harm, a kill switch to stop instantly, a named person who responds, and a rollback you've actually tested.

The underlying logic is Boehm's spiral (L5): attack the riskiest thing first, and spend more only after the risk is understood. "The spiral does not make software cheaper. It makes failure cheaper."

Real cases

Why the gradual path wins

FBI Virtual Case File → Sentinel. A single-pass rewrite, with requirements never baselined, wrote off about $170M with nothing delivered. Restarted with small teams and short cycles, Sentinel shipped in 2012. Same organization, same problem, different lifecycle.
L4, L11; Goldstein, IEEE Spectrum 2005
Knight Capital, 2012. New code went to 7 of 8 servers. On the 8th, dormant code woke up and sent over 4 million orders. About $460M was lost in 45 minutes. It was a deployment failure: no automated verification, dead code left in the build, no kill switch.
L2, L3; SEC File 3-15570
In our agent

What "cut over" requires

  • No "done except deployment" (L5's Definition of Done). A component isn't ready until rollback is tested and you can see which version is live.
  • Before cutover, ask about dead and dormant code in the component.
  • Track how much of the old path has been retired. Deleting the old code is part of done.
Trap: the strangler that never finishes. Chrysler's C3 payroll project, where XP was born, never fully replaced its predecessor and was cancelled in 2000 (L5). Running both systems forever doubles the cost.
Check yourself

Your component matches 99.5% and passes all tests. Name two things that still block cutover.

Write an answer first.

Any two of: an untested rollback; no way to tell which version is live; no canary or kill switch; no named response owner; dormant code nobody has asked about; the remaining 0.5% not yet classified (one of those mismatches could be a money or compliance bug).

Shadow runs and the oracle

How you know the new version is correct, and why "matches the old one" isn't the same thing.

In plain words

Run both, compare, but who's the judge?

Send real traffic through the old and new versions side by side and compare outputs. Simple. The hard part is deciding what counts as "correct" when they differ. The thing you compare against is called the oracle. It's tempting to make the old system the oracle. That's the mistake.

How it actually works

Four rules for a fair comparison

  1. Measure noise first. Run two copies of the old code against each other. Timestamps, random IDs, and ordering differ even when both are right. Subtract that noise from the old-vs-new diff (Twitter Diffy's technique).
  2. Only the old path commits. The new path runs against mocks or a sandbox so there are no duplicate charges or emails.
  3. Compare effects, not just return values. In L18, openLock() returned nothing while the audit log said OPENED: the system couldn't tell "decided to open" from "opened." Compare the rows written and messages sent.
  4. Keep the judge separate. The model that rewrote the component never grades it.
Real cases

When the oracle is wrong

UK Post Office Horizon. The court found 25 defects with the potential to affect branch accounts. But the authority to assert the accounts were correct sat with one party, and the other side had no way to inspect or challenge it. The system was trusted over people. Over £1.7 billion in redress has been paid to more than 14,000 claimants.
L17; Bates v Post Office [2019] EWHC 3408 (QB)
Toyota "Task X." One software task ran the throttle, cruise control, and all five fail-safe modes. When it died, the mechanisms meant to notice the failure died with it. "A class that holds a power and its own audit has no audit."
L17; Bookout v. Toyota, 2013
In our agent

Design consequences

  • "Old is correct" is never the default. A person confirms it, especially where old output can't be independently checked.
  • Generated tests must pin exact values and every state change. LLM-written postconditions were complete only 21–26% of the time, and 78% left the return value under-constrained (PostcondBench, L17).
Trap: Goodhart's law. "When a measure becomes a target, it ceases to be a good measure" (L5). If 99% match is the goal, the cheapest way to reach it is marking fields "doesn't matter" or copying old bugs. Every ignore rule needs an owner's sign-off, and the dashboard shows how many mismatches were waved off.
Check yourself

Old and new disagree on 3% of requests. Two copies of the old code also disagree with each other on 2%. What's your real mismatch rate, and what do you do next?

Write an answer first.

Roughly 1% is real (3% minus 2% noise, assuming the noisy fields overlap). Next, classify that 1%: provable defects get fixed, and unmade decisions go to an owner (Chapter 8). Also check what made old-vs-old differ, and add those fields to the comparison's ignore rules with sign-off.

What replay can't see

A shadow run only tests what already happened. These failures live outside that window.

In plain words

History is a biased sample

Replaying last week's traffic tells you the new version handles last week. It says nothing about the storm that hasn't come yet, the counter that overflows next year, or two requests racing at peak. Each blind spot needs its own test.

How it actually works

Six blind spots, each with a real failure

Blind spotWhat happenedTest to add
Events that never occurredSouthwest 2022: 16,900 flights cancelled; "a use case that nobody defined." Humans with telephones were the integration layer (L15)Synthetic rare scenarios: outages, bursts, irregular operations
Concurrency at peakCometPark: every sensor passed alone; 40 at once at 9:50 double-counted (L3)Replay at peak concurrency, end to end
Time accumulationBoeing 787: a counter overflowed after 248 days, dropping all AC power (L17)Check field widths; long-horizon tests for time logic
A check made too earlyAWS US-EAST-1, Oct 2025: staleness checked at the start, trusted until the write; about 14.5 hours of disruption (L17)Reorder and delay events; flag check-then-use gaps
Silent defaultsGoogle Cloud 2024: a blank field defaulted to one year; a customer environment was deleted with no notice (L17)Ask about every implicit default the old code relies on
Same value, different meaningMars Climate Orbiter: pound-force vs. newton seconds, never stated in the interface; $328M lost (L3)A per-field glossary with units and meaning
Inherited assumptions

Correct code in the wrong world

Ariane 5, 1996. Software reused from Ariane 4 converted a 64-bit value to a 16-bit integer with no guard. On Ariane 4 the value could never get that big. On Ariane 5 it did, and the rocket was destroyed at 37 seconds. "The code was correct — for a different rocket."
L3; ESA/CNES Inquiry Board, 1996
Therac-25. Software was reused from an earlier model and hardware interlocks were removed because the software was trusted to replace them. There were six massive radiation overdoses.
L3; Leveson and Turner, 1993
In our agent

What this changes

  • Never silently drop a legacy guard, range check, or interlock during a rewrite. Ask why it's there.
  • Separate language and library noise (rounding, floats, date handling) from real logic differences. Airbus lost about two years when two teams' CAD versions computed bend radii differently (L3).
Check yourself

The legacy code checks that an amount is under 10,000 before processing. The rewrite drops it because "no recorded request was ever that large." What's wrong with that reasoning?

Write an answer first.

The recorded traffic is history, not the full input space; that's the Ariane 5 mistake in reverse. The check may encode a business rule (approval limits) or protect something downstream. It's a question for a person, and the guard stays until they answer.

What a requirement is

The unit your agent produces every time a person answers.

In plain words

A need someone can check

A requirement is a statement of need that someone can check. "The system shall be user-friendly" isn't a weak requirement. It isn't a requirement at all, because nobody can be wrong about it, so nobody can be right either.

How it actually works

Four properties, three kinds

A requirement needs all four of these. Drop one and you have a wish, a note, or an argument waiting to happen (L9):

  1. Need: something a stakeholder must be able to do, or a quality the system must have
  2. Stated: written in one place, in words everyone reads the same way
  3. Checkable: someone can tell, without argument, whether it's met
  4. Owned: a named person answers questions and approves changes
KindWhat it doesExample
FunctionalAdds behavior"Shall let a rider save a favorite stop"
QualitySays how well"Saved stop loads in under 1 second"
ConstraintRemoves options"Must run on existing university servers"

Make it testable by adding a number, a condition, and who it applies to. "Accurate" becomes "90% of predictions within 2 minutes of actual, measured weekly."

Hunt ambiguous words: vague quantifiers (fast, most), undefined actors (the user, they), hidden alternatives (and/or, etc.), and escape words (normally, where possible). "The panel should normally update quickly for most users" has four ambiguities in nine words.

A real case

"Responsive" isn't a specification

Hertz v. Accenture, 2019. A website rebuild that never launched; Hertz sued for over $32M in fees paid (the parties later settled). Both sides agreed on the goal. The dispute was over what had actually been specified and who owned the turn-by-turn behavior. With no agreed description, "it does not work" became a matter of opinion.
L13; allegations are Hertz's pleadings, not findings
In our agent

Every answer passes the four-property test

When a person clicks "Old is correct," the agent writes the rule as a checkable statement with an ID and an owner (the person who answered), then generates a test from it. The agent also flags ambiguous words in its own questions before sending them.

Check yourself

Rewrite as a testable requirement: "Late fees should be calculated correctly."

Write an answer first.

One version: "For an account paid N days late (N ≥ 1), the late fee shall be 1.5% of the overdue balance per day, truncated to the cent, capped at $25. Owner: Finance lead." The fix always adds a number, a condition, and an owner. The real numbers come from the person, not from you.

Is "It must use a PostgreSQL database" a requirement? If not, what is it?

Write an answer first.

Usually a design decision, because it answers HOW, not WHAT. It's only a constraint if something outside the team imposes it (IT policy, an existing contract). Ask who requires it and why (L9's requirements clinic).

Why people can't just tell you

The core of the communication layer: matching the question to the gap.

In plain words

The curse of knowledge

The person who knows the system pictures the version in their head, not the one they've described. In Şeker's classroom exercise, the proposer's estimate grew after being interviewed, even though nothing about the idea changed. "The interview did not add it — it revealed it" (L7).

How it actually works

Three reasons, six techniques

  1. They describe solutions. "Put a big refresh button" really means "I can't tell if these times are current." Ask why until you reach something that would stay true if the technology changed.
  2. They leave out the obvious. The most important facts go unsaid because everyone takes them for granted. This is the dangerous one.
  3. They can't imagine what they haven't seen. Give them something to react to.
The gapTechniqueAgent version
Need broad coverageClosed interviewStandard questions per component: who uses it, what happens when it fails, what must it NOT do
Something important is unsaidOpen interview + whyFollow-ups in the same thread
Steps done on autopilotScenario walkthrough"Walk me through the last time this broke"
Say vs. do may differObservationOpt-in screen recording, production logs
Rules, history, regulationDocument studyRead commits, tickets, docs before asking
They can't picture itPrototypeShow both outputs side by side

"No technique is best. The question is which gap you are facing right now" (L9). And a session ends with a written, agreed record plus a list of unknowns. "The feeling is not a deliverable."

A real case

The GPS line nobody asked for

In L9's CometShuttle notes, a driver said: "The GPS drops in the parking garage. Every time." Nobody had asked about GPS. It came out of an open interview and could reshape the whole system. That's the kind of fact a fixed question list never finds.
CometWash role-play (L10). Each stakeholder holds a secret they reveal only if asked the right question: the vendor contract forbids third-party hardware; three of 24 machines are always down and the "done" signal fires four minutes early; a resident doesn't want anyone to know when they do laundry. This is the template for our demo and our evaluation set.
In our agent

Who, how, and the stakeholder map

  • Who: sort stakeholders by influence and impact. Route by role, not by name; one person may hold three roles, and external systems are actors too.
  • How: diagnose the gap type, then pick the question style from the table. Ask for examples, not opinions.
  • After: send the write-up back to confirm before it becomes a test.
Check yourself

A finance lead says "the report needs an export button." Using the why-ladder, what might the real requirement be, and why does it matter for the rewrite?

Write an answer first.

The button is a solution. The need might be "I reconcile these numbers in Excel every Monday" or "the auditor needs a copy." That changes what to build: maybe a scheduled feed, maybe fixing the numbers so manual reconciliation isn't needed. It also reveals a hidden human integration step, the Southwest pattern.

Defects vs. unmade decisions

The single most important rule for when the agent should interrupt a person.

In plain words

Two kinds of "this looks wrong"

A defect contradicts something already agreed (a requirement, a decision record, the architecture), and you can prove it from that material. A defect gets fixed. Nobody needs to be asked.

An unmade decision isn't settled anywhere. Two reasonable people could choose differently. It needs an owner and a justification, not a correction (L18).

How it actually works

The engineer's authority stops at business calls

In the L14 CometPrint exercise, the brief never said whether to debit print quota before or after printing. Debit first and a paper jam means the student paid for nothing; print first and a failed debit means free pages. Groups that picked one "produced the tidier sheet — and made a business decision it had no authority to make." Writing "could not decide, ask Print Services" scored full marks.

When two mandatory requirements can't both hold (L16: a door must open during a network outage, but a revoked card must stop working within five minutes), no clever design saves you. Lay out both options with their costs and hand the choice to whoever is entitled to make it. The decision record stays Proposed until they answer.

A design is finished not when every question is answered, but when every unanswered question has a name against it.
Şeker, L18
Practice

Sort these mismatches

In our agent

Why this cuts interruptions

Only unmade decisions become Slack questions. Defects get fixed against the record. Conflicting answers from two people go back to both of them to clarify. Never pick one, never average, never model both (L10, L11).

Check yourself

Old code deletes unpaid orders after 30 days and notifies nobody. Defect or unmade decision? Who do you ask?

Write an answer first.

Unmade decision, unless a requirement already says customers must be notified. It mirrors L14's "deleted unprinted, nobody is told": decision or oversight? Only the business owner (for example the operations or customer-support lead) can say. Keep the old behavior until they answer.

Traceability and change

How knowledge stays connected to code, and how it survives people changing their minds.

In plain words

A thread from need to test

Traceability is a thread you can follow both ways: need → requirement → design → code → test. Backward, it answers "who asked for this?" Forward, it answers "what breaks if this changes?"

How it actually works

Baselines, change control, gaps

  • Baseline: the agreed, versioned reference. "A baseline is not a freeze. It is the reference you measure a change against" (L10).
  • Change control: record the request → assess impact (using the forward trace) → the owner decides → revise the baseline. Skip a step and it's creep, not change.
  • Reading the matrix (L11): a blank row is a requirement nothing realizes. A blank column is a feature nobody asked for. One requirement spread over eight use cases means the requirement is too coarse.
  • Fitness functions (L16): automated checks that keep a decision true after everyone has forgotten it, running on every build.
A real case

Nothing to measure against

FBI Virtual Case File. Requirements were never frozen, several hundred change requests were absorbed, and there was no agreed reference version, so the delivered system couldn't be verified against anything. "A baselined model is the thing a change request gets measured against — and there was none" (L11).
In our agent

Decision records do this automatically

  • Each answer records the question, evidence, who answered, when, and the test it produced. That's the backward trace.
  • Before porting legacy code, check for a blank column: code nobody asked for. Ask "who asked for this?" But an empty row for something deliberately outside the boundary is correct, so don't flag every one.
  • Records get a review date. "An out-of-date model is worse than no model, because someone will trust it" (L11).
Check yourself

A teammate says "we'll just add the EV-charging field while we're in there." Under change control, what happens instead?

Write an answer first.

Record the request with the requester's name, assess the impact by tracing what it touches (cost, schedule, other requirements), let the owner accept, reject, or defer it with a reason, then revise the baseline. "Creep is not caused by the customer asking. It is caused by the team answering without assessing" (L7).

Built right vs. right thing

Why a perfect match with the old system can still be a failure.

In plain words

Two different questions

Verification: did we build the thing right, matching the spec? Validation: did we build the right thing, meeting the actual need? Boehm's distinction (1979). A shadow run is verification. Only a person who has the need can validate.

How it actually works

Validation always needs a human

"You cannot validate against a document. Validation always needs someone who has the need" (L10). Verification checks against tests, reviews, and inspection. Validation needs a user, a prototype, or a demo.

Real cases

Passed every test, failed every user

CometPark v1.0. It met REQ-14 (±3 vehicles in 97% of readings), shipped on schedule, and was signed off. Daily users collapsed within three months. "Garage 4 — 37 spaces free" doesn't tell you which level, so students still circled for ten minutes. v2.0, two years later, showed per-level counts: search time fell from 9.4 minutes to 2.8. "One more question in elicitation would have cost nothing."
L3, L5
Denver Airport baggage system. Components met their specifications. The system never worked; bags were shredded and misrouted, and it was abandoned in 2005.
L3
In our agent

Matching the old system is verification only

A 99% match proves the rewrite behaves like the old system. It doesn't prove the old system was right. That's why decision records go back to a person to confirm, and why health metrics after cutover (DORA's deployment frequency, lead time, change failure rate, recovery time) are watched as trends, never as targets (L6).

Check yourself

Label each as verification or validation: (a) replaying traffic through old and new, (b) a finance lead confirming the rounding rule, (c) a unit test generated from her answer.

Write an answer first.

(a) Verification: checks against existing behavior. (b) Validation: a person with the need confirms it's the right behavior. (c) Verification: it checks the code against the now-validated rule.
